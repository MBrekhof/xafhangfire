## 2. Password hashing (decision 2a: mixed)

Both apps set `DefaultSettingsCompatibilityMode = Latest` (Blazor.Server/Program.cs:40, Win/Program.cs:45). In 26.1,
`Latest` switches `PasswordCryptographer` to SHA512-600K only, so stored SHA1 hashes would stop verifying
(26.1 source `PasswordVerifier.cs:51-59`; dxdocs 112649). Add directly after the mode line in **both** files (shared DB):

```csharp
DevExpress.Persistent.Base.PasswordCryptographer.UseSHA1_20K = true;    // existing SHA1 hashes keep verifying
DevExpress.Persistent.Base.PasswordCryptographer.UseSHA512_600K = true; // new/changed passwords use SHA512-600K
```

State today: Admin and User have empty passwords (stored `""`, verified before any algorithm runs, unaffected);
HangfireJob has a random SHA1 hash nobody logs in with (XafJobScopeInitializer signs in without a password). The
AUTH-002 guard `ComparePassword(string.Empty)` (Updater.cs:429) keeps working under the mixed setting.

## 3. Dropping the legacy timestamp switch (JOB-013 decision 1b)

Remove `AppContext.SetSwitch("Npgsql.EnableLegacyTimestampBehavior", true)` (Blazor.Server/Startup.cs:44). The Win app
never set it (WIN-001).

The app has exactly 8 DateTime columns, all `timestamp without time zone` (JobDefinitions.LastRunUtc/NextRunUtc,
JobExecutionRecords.StartedUtc/CompletedUtc, PermissionPolicyUser.LockoutEnd, ProjectTasks.DueDate,
Projects.StartDate/DueDate). No EF migrations; XAF's updater owns the schema. The DB session time zone is UTC.

In modern mode EF maps DateTime to `timestamptz` by default and EF sends explicitly typed parameters, so:
- Kind=Local/Unspecified writes or LINQ parameters fail ("Cannot write DateTime with Kind=Unspecified to …
  timestamp with time zone") — reproduced in `tsconv.cs`, and the reason WIN-001 is likely broken today;
- if only the column type is fixed to `timestamp`, Kind=Utc fails instead ("Cannot write DateTime with Kind=UTC to
  … timestamp without time zone") — e.g. `DateTime.UtcNow` in XafJobExecutionRecorder and XAF's own
  `UserLockout` (`LockoutEnd = DateTime.UtcNow…`, 26.1 source UserLockout.cs:108,117).

Fix: a model convention in `xafhangfireEFCoreDbContext` (shared by both apps):

```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder configurationBuilder)
{
    // UPG-001/JOB-013: no Npgsql legacy timestamps. DateTime columns stay `timestamp without time zone` and keep
    // the wall-clock value as written (what the legacy switch did); Kind is dropped on the way in.
    configurationBuilder.Properties<DateTime>().HaveColumnType("timestamp without time zone").HaveConversion<UnspecifiedKindConverter>();
    configurationBuilder.Properties<DateTime?>().HaveColumnType("timestamp without time zone").HaveConversion<UnspecifiedKindConverter>();
}
```

with `UnspecifiedKindConverter : ValueConverter<DateTime, DateTime>(v => DateTime.SpecifyKind(v, Unspecified), v => v)`.

Verified (scratchpad `tsconv/tsconv.cs` on Npgsql EF 8.0.11, and the MS research probe on EF 10 + Npgsql EF 10.0.3):
- writes of Kind=Utc, Local and Unspecified all succeed and store byte-for-byte what the legacy switch stores
  (Local stays local wall clock, as today; the only `DateTime.Now` writers in the repo are non-persistent);
- the converter is applied to LINQ parameters (Kind=Utc and Unspecified cutoffs both match);
- read-back Kind is Unspecified, as today.

Known limit (both modes): `DateTime.UtcNow` written *inside* a LINQ predicate against these columns is translated to
`now()` (timestamptz) and throws "Cannot apply binary operation on types 'timestamp with time zone' and 'timestamp
without time zone'". The repo never does this (values are captured as parameters); stored report layouts contain no
date functions in filters (checked in ReportDataV2); the two `Now()` uses are print-time ExpressionBindings.

`-infinity`: PermissionPolicyUser.LockoutEnd holds `-infinity` today (legacy wrote DateTime.MinValue that way).
Modern Npgsql keeps the MinValue ↔ -infinity mapping by default; checked live by logging in (step 5).

Hangfire: its own connection, `timestamptz` columns, Kind=Utc values. With the switch gone, `fetchedat` reads back as
Kind=Utc and `fetchedat = @fetchedAt` matches (keep-alive, RemoveFromQueue, Requeue) — verified in `tsrepro.cs modern`
and the MS research probe on Npgsql 10.0.3. The 123 stale queue rows of finished jobs are expected to clear on their
own: their `fetchedat` is older than the 30-min invisibility timeout, so a worker re-fetches each one, finds it no
longer Enqueued, and RemoveFromQueue now matches. If they don't clear, delete them once by SQL.

Comment update: InterruptedRuns.cs:42 names the legacy timestamps as the reason dates are compared in memory; reword
(the in-memory comparison stays — it is correct and needs no SQL).

DX departure, stated: DX's 26.1 template still emits the legacy switch for PostgreSQL. Dropping it is Martin's
decision (JOB-013 1b); the convention covers the one DX write found (UserLockout).
